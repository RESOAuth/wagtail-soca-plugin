# Security and deployment decisions

This is an MVP implementation profile, not a certification or external audit.

## Identity and authority

Authentication requires an OIDC ID token from the exact configured issuer. Algorithms are explicitly pinned to ES256 or RS256; signatures require exactly one matching provider `kid`, appropriate key type/use and a P-256 or at least 2048-bit RSA public key. Remote key headers, symmetric algorithms and unsupported JOSE extensions are refused. Provider JWKS are fetched fresh for each login; there is no stale-key cache.

Required claims include issuer, subject, audience, expiry, issue time and nonce. `azp` is required with multiple audiences and checked when present. Times must be integers, with 60 seconds of clock tolerance; issue time must be within the transaction window and lifetime at most 24 hours. Token/code hashes are checked when present. Optional UserInfo must match the verified subject and cannot contradict ID-token email claims. Email verification must be the JSON boolean `true`.

Account selection deliberately follows the WordPress plugin's current verified-email matching model, rather than permanently linking issuer/subject. Changing or reassigning provider/local email can change which account is selected. Duplicate local emails fail closed. Existing active users also need `wagtailadmin.access_admin`; Django `is_staff` is not a substitute for Wagtail permissions. Existing usernames, emails, passwords, groups and privilege flags are preserved; blank names may be filled after successful admission. Users are never promoted or re-enabled. Custom user models must expose an email field through Django's `get_email_field_name()` API and standard permission methods.

Account creation is explicitly opt-in (`CREATE_USERS`, default false). A missing local account is created only after signed-token validation, verified-email checks and allow/deny admission. `NEW_USER_GROUP` must reference an existing group with `wagtailadmin.access_admin`; the form lists only eligible groups and the callback rechecks eligibility. New users receive that one group, an unusable password, `is_active=True`, `is_staff=False` and `is_superuser=False`. Provider role/privilege claims are ignored. Choose group permissions carefully, particularly when allowing an entire email domain. Creation and group membership are atomic and roll back on failure. Disabling creation does not revoke existing accounts or sessions, and subsequent group permission changes follow normal Wagtail semantics.

Provisioning supports Django's standard User and compatible custom models with standard password/permission/group/flag fields, a unique textual `USERNAME_FIELD`, and no additional `REQUIRED_FIELDS` beyond email. Non-email usernames must allow at least 37 characters. Accounts are initially inserted with `soca_` plus a deterministic SHA-256 email digest, truncated to the field length (at least 128 digest bits). A duplicate-email recheck occurs before any rename. Within the same transaction, a new account can receive a validated, available `preferred_username`, or an email-local-part plus 12 hash characters; case-insensitive collisions/invalid values fall back safely. The `soca_` namespace is reserved; the initial identifier is the final fallback. Email usernames remain the normalized email. The initial unique insert and post-insert email check make concurrent same-email plugin logins converge even if their preferred usernames differ; a losing creation rolls back and may reuse the eligible matching account. Profile usernames never link/select an existing account. Field validators and lengths are checked; incompatible models fail closed. Model defaults/signals must be compatible with these semantics. Provisioning deliberately constructs and saves the model rather than invoking a custom manager's `create_user`; projects needing manager-specific onboarding must implement that separately before enabling this feature. Django's default email field is not database-unique: external account-creation paths must enforce case-insensitive email uniqueness too to prevent cross-system races.

Profile defaults run only after verified-email admission and local account eligibility. `given_name`/`family_name` fill only blank `first_name`/`last_name`; existing values are preserved using conditional updates, not unconditional saves. A full `name` is used whole as `first_name` only when structured names are unavailable and both local fields are blank. No surname guessing is performed. Only non-unique CharFields that are not identity/email fields are eligible. Text types, Unicode normalization, whitespace, markup/control rejection, length limits and field validators are checked. Signed ID-token values have priority; missing usable profile fields may be filled from UserInfo after exact subject and non-contradictory email/verification checks. UserInfo retrieval for profile defaults is optional; required verified-email fallback still fails closed. No avatar fetching, locale/preference writes, role mapping or identity-field synchronization occurs. Profile values are not logged.

**Trust decision:** an upstream provider able to verify an allowed administrator email can authenticate as that administrator. Email verification alone is not an MFA assurance claim. Retain a local administrator password and assess the provider's identity lifecycle.

## Transactions and sessions

Each start creates independent random state, nonce and PKCE verifier. State and browser binding are stored as SHA-256 digests. Nonce, verifier, provider endpoints, destination and configuration fingerprint are encrypted with Fernet under a domain-separated key derived from Django `SECRET_KEY`. Pending transactions expire after ten minutes. An atomic conditional database update claims the transaction once across workers before the code is redeemed; failed callbacks cannot retry a consumed transaction.

An independent browser-binding secret lives in a server-side Django session. Callbacks without that session are refused, including callback URLs copied to another browser. Secure, HttpOnly, SameSite=Lax session cookies should be used; Lax permits the top-level GET redirect from the provider. Signed-cookie sessions are unsupported. Do not use a process-local cache for sessions in multi-worker deployments. Django login rotates the session key and its normal authentication/session semantics apply thereafter.

Configuration changes, including keys or policy, invalidate pending transactions. All workers must share the same configuration, key, database and server-side session store. Changing `SECRET_KEY` invalidates encrypted transactions; `SECRET_KEY_FALLBACKS` is intentionally not used for them. Existing logged-in sessions are governed by Django, not retroactively rechecked against admission lists; revoke those sessions through the host application when necessary.

The **Settings → SOCA** screen is restricted to active Wagtail superusers and all writes/checks require POST and CSRF protection. Nonsecret provider and admission settings are stored in one application-wide database row and take effect on the next request, overriding their deployment defaults. The private key and site origin are deployment-only; even injected database fields cannot override them. Each save records the local administrator and a new revision, invalidates pending SSO transactions, and rejects stale editor revisions. Deployment system checks deliberately avoid database access so migrations can run before the settings table exists. Saved settings are validated before being accepted. Connection checks fetch only the saved configuration and log no claims or secrets.

Only local absolute-path destinations are accepted. Responses containing state/codes are never cached and set `Referrer-Policy: no-referrer`. Callback duplicates, issuer mismatches and provider errors fail closed. Django sessions contain no provider tokens; access tokens exist only during exchange/UserInfo requests. Logs use fixed reason codes and local user IDs, never provider response bodies, claims or tokens. Configure proxies and exception monitoring to redact OAuth query parameters and request-local secrets. Keep Django DEBUG disabled in production.

The temporary claim inspector is off by default, separate from SSO configuration, and restricted to active superusers for viewing, arming and clearing (POST/CSRF for mutations, no-store responses). Arming authorizes capture of the next successful admitted SSO login **installation-wide**, including another user's identity; operators must obtain appropriate permission before using it. Failed authentication/admission never produces a report. It does not alter account attributes or permissions. A diagnostic-only UserInfo request is made while armed if possible, checks the exact subject, and does not make otherwise valid sign-ins fail when profile retrieval is unavailable. Normal verified-email fallback remains mandatory and unchanged.

Reports show ID-token claims separately from subject-matched UserInfo. Only a fixed allowlist of basic identity, profile and protocol metadata values is retained; unknown/nested values, nonce, token hashes and provider session identifiers are redacted. Claim names remain visible. Profile strings and string lists are bounded and template-escaped. Raw JWTs/access tokens are neither persisted nor logged. The sanitized report is encrypted with Fernet using a domain-separated key derived from Django `SECRET_KEY`, without fallback keys. An atomic revision/empty-payload/expiry conditional update makes capture one-shot across workers and prevents stale callbacks overwriting a new arm or clear. Arming lasts ten minutes and capture has a new ten-minute visibility/decryption TTL. Expired rows are deleted when the inspector is accessed or by `soca_cleanup`; run cleanup regularly and account for database/backups in retention policies. Clearing removes the live row, not existing backups. Database administrators with access to both the database and Django secret can decrypt unexpired reports. Never leave a diagnostic armed unnecessarily.

## HTTPS and network boundaries

All URLs require HTTPS and public ASCII DNS names; IP literals, userinfo, fragments, dot segments and control characters are refused. Each server fetch resolves DNS, rejects the entire answer if any address is nonpublic, then connects to a validated address while validating the original TLS hostname and sending that hostname as SNI/Host. No environment proxies, redirects or implicit retries are used. JSON responses must be HTTP 200, uncompressed and at most 256 KiB. Socket timeouts are 3 seconds to connect and 8 seconds to read; these are not a wall-clock deadline for DNS or a slow stream. Apply worker/ingress time limits and egress policy as outer controls.

Discovery must advertise code, S256 PKCE, private_key_jwt, ES256 assertions, an accepted ID-token algorithm and OIDC subject types. Callback issuer is checked whenever present and required when advertised. Otherwise a single pinned issuer and encrypted discovery snapshot form the mix-up boundary. Discovery missing CIMD support requires an actual provider test; explicit false is rejected. No OAuth-only fallback exists.

## Signing key lifecycle

The application reads a persistent unencrypted P-256 PEM from settings supplied through a secret mount or equivalent secret manager. It never stores this key in the database or publishes private material. Protect configuration/backups and mount secrets read-only. Never generate a new key on process startup. Cryptographic key IDs derive from public material, so remain stable across workers and restarts.

Version 0.0.1 publishes a single key and does **not** implement overlapping rotation. Rotate in a planned SSO maintenance window: disable SSO, allow ten-minute transactions to expire, replace the key consistently across workers, purge site/CDN document caches, and coordinate expiry/purge of provider metadata/JWKS caches. Re-enable and run `soca_check`, then test a real login while local password recovery is available. Public documents advertise a five-minute cache; this does not guarantee a provider uses that bound. Do not claim zero-downtime rotation.

With `METADATA_PROXY`, public metadata includes inline JWKS and is encoded as base64url in an HTTPS URL template. Exactly one `%s` placeholder must appear in its path; userinfo, fragments and unsafe URLs are refused. The fetched document must exactly match the generated document, including its exact client ID. Never put secrets, admission lists or user data into metadata. The proxy can observe the public application name, origin, callback and public signing key. Changing metadata/key changes the immutable URL and therefore the client ID; provider consent or pairwise subjects can change. The proxy does not receive the private key, authorization codes or tokens. The normal provider transport and verification apply unchanged.

## Host responsibilities and MVP limits

Use HTTPS, server-side shared sessions, a strong persistent Django secret, current dependency patches and rate limiting. Login start performs discovery and writes a transaction, so ingress limits and regular cleanup matter. Public metadata endpoints must bypass login protection and serve the configured canonical origin. The plugin does not enable automatic SSO redirects or replace local password login. Local logout does not log out of the provider.

The default external provider is RESOAuth at `https://auth.resoauth.cloud`. On sign-in the browser sends an authorization request, the application exchanges the code and signed assertion, and the provider supplies identity claims. Operators are responsible for provider terms/privacy disclosures. No analytics or telemetry are sent by the plugin.
